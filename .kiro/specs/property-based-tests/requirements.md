# Requirements Document

## Introduction

This feature adds a property-based test suite to the `examples/demo-bug-repo` project to verify the correctness of the authentication validation utilities in `src/validation.js`. The suite uses `fast-check` as the property-based testing library and is demonstrated as part of the Kiro University Challenge (Lesson 1: Specs, Lesson 4: Property-Based Testing).

The suite targets four correctness properties:
1. Crash-freedom of `validateEmail` on any non-string input (exposing the documented null/undefined bug)
2. Acceptance of well-formed email strings by `validateEmail`
3. Rejection of passwords shorter than 8 characters by `validatePassword`
4. Consistency between `validateLoginForm` and its component validators

The existing `tests/validation.test.js` remains unchanged; the new file is `tests/validation.property.test.js`.

---

## Glossary

- **Test_Suite**: The file `examples/demo-bug-repo/tests/validation.property.test.js` that contains all property-based tests.
- **Validator**: Any of the three exported functions in `src/validation.js` — `validateEmail`, `validatePassword`, or `validateLoginForm`.
- **fast-check**: The open-source property-based testing library installed as a dev dependency in `examples/demo-bug-repo/package.json`.
- **Arbitrary**: A `fast-check` generator that produces random values of a specified shape or type.
- **Property**: A boolean invariant that must hold for all inputs generated by an Arbitrary.
- **Non-String_Input**: Any JavaScript value that is `undefined`, `null`, a number, a boolean, an object, or an array — i.e., `typeof value !== 'string'`.
- **Valid_Email_String**: A string matching the regular expression `^[^\s@]+@[^\s@]+\.[^\s@]+$`.
- **Short_Password**: A string whose `.length` is strictly less than 8.
- **ValidationResult**: An object with at least a boolean `valid` field, and an optional string `error` field when `valid` is `false`.

## Requirements

### Requirement 1: Install fast-check as a Dev Dependency

**User Story:** As a developer, I want `fast-check` available in the demo-bug-repo project, so that the property-based test file can import and use it without a runtime error.

#### Acceptance Criteria

1. THE `demo-bug-repo` project's `package.json` SHALL list `fast-check` under `devDependencies` with a pinned major version (e.g., `"fast-check": "^3.0.0"` or newer stable release).
2. WHEN `npm install` is run inside `examples/demo-bug-repo`, THE package manager SHALL resolve and install `fast-check` without error.
3. WHEN the `Test_Suite` imports `fast-check`, THE Node.js module resolver SHALL locate the package without throwing a `MODULE_NOT_FOUND` error.

---

### Requirement 2: Property — validateEmail Must Not Throw on Non-String Input

**User Story:** As a test engineer, I want a property that verifies `validateEmail` never throws on arbitrary non-string inputs, so that the known null/undefined crash bug is formally captured and will block merging until fixed.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "validateEmail does not throw for any non-string input".
2. WHEN `fast-check` generates a Non-String_Input via `fc.oneof(fc.constant(undefined), fc.constant(null), fc.integer(), fc.boolean(), fc.object(), fc.array(fc.anything()))`, THE `Test_Suite` SHALL wrap the call to `validateEmail(input)` inside `assert.doesNotThrow`.
3. WHEN the property is run and `validateEmail` throws for any generated input, THE `Test_Suite` SHALL report the failing example, causing the test run to exit with a non-zero code.
4. WHEN the property passes (i.e., no throw is observed for all generated samples), THE `Test_Suite` SHALL record the test as passed.
5. THE `Test_Suite` SHALL run this property with at least 100 generated examples (fast-check default).

---

### Requirement 3: Property — validateEmail Returns { valid: false } for Non-String Input

**User Story:** As a test engineer, I want a property that verifies `validateEmail` returns a `{ valid: false }` ValidationResult for any Non-String_Input after the crash bug is fixed, so that the fix is complete and not merely non-crashing.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "validateEmail returns { valid: false } for non-string input".
2. WHEN `fast-check` generates a Non-String_Input, THE `Test_Suite` SHALL assert that the `valid` field of the returned ValidationResult equals `false`.
3. THE `Test_Suite` SHALL run this property with at least 100 generated examples.

---

### Requirement 4: Property — validateEmail Returns { valid: true } for Valid Email Strings

**User Story:** As a test engineer, I want a property that verifies every well-formed email string is accepted by `validateEmail`, so that the validator does not produce false negatives on valid inputs.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "validateEmail accepts any valid email string".
2. THE `Test_Suite` SHALL generate Valid_Email_String values using a `fast-check` Arbitrary composed of `fc.emailAddress()` or an equivalent tuple-based builder that satisfies the `^[^\s@]+@[^\s@]+\.[^\s@]+$` regex.
3. WHEN `fast-check` generates a Valid_Email_String, THE `Test_Suite` SHALL assert that the returned ValidationResult has `valid === true`.
4. THE `Test_Suite` SHALL run this property with at least 100 generated examples.

---

### Requirement 5: Property — validatePassword Rejects Short Passwords

**User Story:** As a test engineer, I want a property that verifies any string shorter than 8 characters is rejected by `validatePassword`, so that the minimum-length invariant is proven for the entire input space rather than spot-checked.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "validatePassword rejects any string shorter than 8 characters".
2. THE `Test_Suite` SHALL generate Short_Password values using `fc.string({ maxLength: 7 })`.
3. WHEN `fast-check` generates a Short_Password, THE `Test_Suite` SHALL assert that the returned ValidationResult has `valid === false`.
4. WHEN `fast-check` generates a Short_Password, THE `Test_Suite` SHALL assert that the returned ValidationResult has `error === 'Password must be at least 8 characters'`.
5. THE `Test_Suite` SHALL run this property with at least 100 generated examples.

---

### Requirement 6: Property — validateLoginForm Is Consistent with Component Validators

**User Story:** As a test engineer, I want a property that verifies `validateLoginForm` produces the same outcome as calling `validateEmail` and `validatePassword` independently, so that composite logic does not introduce silent inconsistencies.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "validateLoginForm is consistent with validateEmail and validatePassword".
2. THE `Test_Suite` SHALL generate form-data objects using `fc.record({ email: fc.string(), password: fc.string() })` to cover arbitrary string combinations.
3. WHEN `fast-check` generates a form-data record, THE `Test_Suite` SHALL compute `emailResult = validateEmail(formData.email)` and `passwordResult = validatePassword(formData.password)`.
4. IF `emailResult.valid` is `false`, THE `Test_Suite` SHALL assert that `validateLoginForm(formData).valid` is also `false`.
5. IF `emailResult.valid` is `true` AND `passwordResult.valid` is `false`, THE `Test_Suite` SHALL assert that `validateLoginForm(formData).valid` is also `false`.
6. IF `emailResult.valid` is `true` AND `passwordResult.valid` is `true`, THE `Test_Suite` SHALL assert that `validateLoginForm(formData).valid` is also `true`.
7. THE `Test_Suite` SHALL run this property with at least 100 generated examples.

---

### Requirement 7: Test File Is Compatible with the Existing Test Runner

**User Story:** As a developer, I want the new property test file to run using the same `node:test` runner command already configured in `package.json`, so that no additional tooling or scripts are required.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL use `import { test, describe } from 'node:test'` as its test framework.
2. THE `Test_Suite` SHALL use `import assert from 'node:assert/strict'` for all assertions.
3. THE `Test_Suite` SHALL import `fast-check` using the ESM syntax `import * as fc from 'fast-check'`.
4. WHEN the command `node --test tests/validation.property.test.js` is executed inside `examples/demo-bug-repo`, THE Node.js runtime SHALL discover and run all properties defined in the `Test_Suite`.
5. THE root `package.json` `test:demo` script SHALL execute both `validation.test.js` and `validation.property.test.js` without requiring separate commands.

---

### Requirement 8: Round-Trip Compatibility — Serialized ValidationResult Structure

**User Story:** As a test engineer, I want a property that verifies the ValidationResult objects returned by all three Validators can be serialized to JSON and deserialized back to an equivalent object, so that the results are safe to transmit over APIs or store in logs.

#### Acceptance Criteria

1. THE `Test_Suite` SHALL define a property named "ValidationResult is JSON round-trip safe".
2. THE `Test_Suite` SHALL generate inputs for each Validator and collect the returned ValidationResult.
3. FOR ALL returned ValidationResult objects, `JSON.parse(JSON.stringify(result))` SHALL produce an object that deep-equals the original result.
4. THE `Test_Suite` SHALL run this property with at least 100 generated examples per Validator.
